# DevMind 生产上线检查清单

本清单是 Go/No-Go 门槛。仓库提供代码与部署基线，但无法替组织完成身份治理、数据分级、托管服务采购、备份恢复、SLO、容量和灾备验证；任一“阻断项”未完成都不应对生产流量开放。

## 1. 身份、权限与入口（阻断项）

- [ ] UI/API 已接企业 OIDC/SSO，禁用匿名访问；离职、禁用、会话过期流程已验证。
- [ ] 用户、团队、租户和仓库级 RBAC 在 API Gateway/BFF 或应用层落地，并有拒绝用例。共享 nginx API key 只代表“可信网关到 API”，不能代表最终用户。
- [ ] `/api/admin/*` 走独立、受审计的运维通道与管理 key。生产前端已隐藏管理页，普通前端 key 绝不提升为 admin。
- [ ] 普通、管理、前端服务、GitHub Webhook、Alert Webhook 密钥相互独立，至少 32 个随机字符；已接企业密钥系统并演练轮换/吊销。
- [ ] 主站和 Webhook 使用独立域名。主站强制 OIDC；Webhook 只开放两个精确路径，分别校验 GitHub HMAC 与 Alert Bearer secret。
- [ ] WAF/API Gateway 已配置来源控制、请求体上限、连接/RPS 限制、异常检测；SSE 长连接经压测调参。
- [ ] 已实现按用户/租户的并发、token、费用和速率配额。Ingress 按 IP 限流不能替代租户配额。
- [ ] 管理操作、需求确认、代码索引、Webhook 和第三方写入具备不可抵赖审计日志与保留策略。

## 2. 数据与外部依赖（阻断项）

- [ ] PostgreSQL/pgvector、Redis、Neo4j 使用非默认账号和托管高可用方案，跨可用区策略满足目标 RTO/RPO。
- [ ] 全部上游 TLS 已验证：PostgreSQL `sslmode=verify-ca|verify-full`（最低 `require`）、`rediss://`、`neo4j+s://`/`bolt+s://`，其它启用的 URL 均为 `https://`。
- [ ] PostgreSQL PITR、Neo4j 备份和 Redis 持久化/恢复策略已配置；在隔离环境完成恢复演练并记录实际 RTO/RPO。
- [ ] 发布前完成数据库备份、`alembic upgrade head` 与 revision 校验；schema 变更采用 expand/migrate/contract，并确认前后版本兼容。
- [ ] 数据库迁移使用独立 DDL 角色，API/worker 运行时账号只保留必要 DML；pgvector 扩展由 DBA 预置。旧库已检查并处理重复 chunk 后才增加唯一约束。
- [ ] Embedding 模型、维度与 `vector(N)` schema 一致；换模型有重建、双写/切换与回滚方案。
- [ ] `/workspace` 只挂载经批准的只读代码卷，`CODE_INDEX_ALLOWED_ROOTS` 最小化；不同租户/敏感级别的代码与图谱已隔离。
- [ ] GitHub/Jira/Confluence/Langfuse/LLM 使用最小权限服务身份，出站域名 allowlist、超时、重试和熔断策略已验证。
- [ ] 非本地环境未配置真实监控/日志源时不会使用 mock；Jira 未配置时不会返回伪造 `DRY-*` 成功。

## 3. 模型与 AI 风险（阻断项）

- [ ] 明确哪些源码、日志、PRD、个人信息允许发送到各模型供应商，并完成法务、隐私、跨境和保留策略评审。
- [ ] Prompt 注入、恶意文档/日志、工具越权、敏感信息回显和输出落库有对抗测试；高风险写操作保留人工确认。
- [ ] 代码审查、RAG 与 RCA 有版本化评测集、最低质量阈值和发布回归；模型/Prompt 变更可追溯、可灰度、可回滚。
- [ ] 设置单请求 token、超时、重试和每日/租户预算；成本告警已验证，Redis 聚合降级会触发告警而非静默漏计。
- [ ] 明确 AI 结论是辅助信息；影响发布、事故处置或工单写入的结果有责任人和人工复核边界。

## 4. 可靠性、容量与可观测（阻断项）

- [ ] 定义可用性、成功率、P95/P99 延迟、SSE 首 token 时间、队列等待时间和任务完成率 SLI/SLO，并配置 burn-rate 告警。
- [ ] API、worker、数据库连接池、Redis 队列、Webhook 失败、外部依赖、LLM token/费用有指标、日志、trace 和关联 request/job ID。
- [ ] 告警有值班路由、分级、抑制、Runbook 与升级机制；完成数据库、Redis、Neo4j、模型供应商和网络故障演练。
- [ ] 使用生产相似数据完成 REST/SSE 并发、长连接、超大 diff/文档、大仓索引与队列积压压测，形成容量模型和扩缩容阈值。
- [ ] API/frontend/worker 至少 2 副本并跨节点分散，PDB 和滚动升级已验证；worker 生产扩缩容优先使用 KEDA/队列深度，CPU HPA 仅作保底。
- [ ] ARQ 任务幂等、过期任务、重试上限、毒任务隔离/DLQ、人工重放和部署期间优雅退出均有演练。
- [ ] readiness 会检查关键依赖，liveness 只检查进程；依赖故障不会因错误 liveness 触发重启风暴。

## 5. 供应链与发布（阻断项）

- [ ] 后端使用带哈希 lock、前端使用 `npm ci`；CI 的 lint、类型检查、单测、迁移 smoke、镜像构建和 K8s schema 校验全部通过。
- [ ] 基础镜像和发布镜像固定 digest，生成 SBOM、漏洞扫描、许可证检查并签名；集群验证签名并阻断高危未豁免制品。
- [ ] 已复核 CI 中 `cryptography` 的三个临时漏洞豁免并完成正式风险签字，或在 `langchain-litellm` 放宽 `<49` 上限后升级并移除豁免；当前强制到期日为 2026-09-15，禁止顺延掩盖。
- [ ] GitHub Actions/第三方 action 固定可信版本或 commit，分支保护、双人审批、最小 workflow permission 和受保护生产环境已启用。
- [ ] 配置与密钥不进入 Git、镜像层、前端 bundle、日志或 CI artifact；完成 secret scanning。
- [ ] 已在预生产执行完整迁移、冒烟、负载和回滚演练；发布有负责人、观察窗口、停止条件和变更记录。
- [ ] 数据库默认向前修复。只有 schema 向后兼容时才允许 `rollout undo`；破坏性迁移必须有单独恢复方案和已验证 PITR 点。

## 6. 基线验证命令

这些命令只验证仓库制品，不代表完成上述组织与环境控制：

```bash
# 后端
cd backend
python -m pip install --require-hashes --no-deps -r requirements-dev.lock
ruff check app tests alembic
ruff format --check app tests alembic
pytest -q

# 前端
cd ../frontend
npm ci
npm run lint
npm test
npm run build
npm audit --audit-level=moderate

# 镜像与 Compose
cd ..
docker build -t devmind/backend:verify backend
docker build -t devmind/frontend:verify frontend
docker compose -f deploy/docker-compose.yml config --quiet
docker compose --env-file /secure/path/devmind.env \
  -f deploy/docker-compose.prod.yml config --quiet
```

Kubernetes 的迁移顺序、OIDC/Webhook 入口和验证命令见 [`../deploy/k8s/README.md`](../deploy/k8s/README.md)。正式签字至少应包含产品负责人、安全、平台/SRE、数据/隐私、值班团队和业务集成负责人。
